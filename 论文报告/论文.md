# 基于LLM的智能电商数据分析智能体的实现

## 摘要

电商平台中的商品评论数量庞大、内容分散且表达方式复杂，用户难以仅凭评分与标签快速判断商品是否值得购买。针对传统评论分析方法难以同时完成真实评论获取、结构化统计分析、语义证据召回及自然语言结论生成的问题，本文设计并实现了一个面向电商评论分析场景的基于大语言模型的智能分析系统。系统围绕真实工程闭环展开，采用前后端分离架构：前端工作台承载会话管理、任务跟踪与结果展示，后端则以任务化协议统一组织消息接入、进度查询与结果回收。
在系统实现层面，本文构建了基于多智能体工作流的分析链路。系统接收用户输入的自然语言问题与商品链接后，先识别商品上下文并准备评论数据，再按需执行统计分析、语义检索与图表生成，最终汇总形成包含文本结论、图表信息与评论证据的结构化分析结果。数据层采用三层结构设计，由 MySQL 保存业务主数据，DuckDB 承担轻量统计分析，ChromaDB 支持评论向量检索。评论数据采集面向真实京东商品页面展开，使系统具备真实评论接入与分析能力。
测试结果表明，系统已完成主链路各关键模块的验证覆盖，任务路由、统计分析、语义检索、图表生成、答案汇总、结果审查与结果持久化均纳入测试范围。模型对比测试进一步表明，不同模型在本系统中的表现存在显著差异，性能较强的模型在分析结论的完整性与稳定性方面更适于承担多阶段评论分析任务。本文工作表明，将大语言模型、任务化分析流程与真实评论数据接入能力相结合，能够有效提升电商评论分析系统的结构化表达能力与结果可读性。

关键词: 大语言模型; 电商评论分析; 多智能体; 任务化工作流; 智能体系统

## Abstract

Product reviews on e-commerce platforms are large in volume, highly fragmented in content, and complex in expression, which makes it difficult for users to judge whether a product is worth buying by relying only on ratings and tags. To address the limitations of traditional review analysis methods in real review acquisition, structured statistical analysis, semantic evidence retrieval, and natural language conclusion generation, this thesis designs and implements an LLM-based intelligent analysis system for e-commerce product review analysis. The system is built as a real engineering loop with a front-end and back-end separated architecture. The front-end workspace is responsible for conversation management, task tracking, and result presentation, while the back-end task-oriented protocol organizes message intake, progress querying, and result retrieval.

At the implementation level, this thesis builds an analysis pipeline based on a multi-agent workflow. After receiving a natural language query and a product link, the system first identifies product context and prepares review data, then selectively performs statistical analysis, semantic retrieval, and chart generation, and finally produces a structured analysis result that contains textual conclusions, chart information, and review evidence. The data layer adopts a three-tier structure: MySQL stores business data, DuckDB supports lightweight statistical analysis, and ChromaDB provides vector-based review retrieval. Review acquisition is performed on real JD product pages, which gives the system the ability to access and analyze real review data.

The test results show that the system already has the conditions to verify the complete main workflow, and key modules such as task routing, statistical analysis, semantic retrieval, chart generation, answer composition, result review, and result persistence have all been covered. Model comparison further indicates that different models show clear performance differences in this system, and stronger models are more suitable for multi-stage review analysis tasks in terms of completeness and stability. The work of this thesis demonstrates that combining large language models, task-oriented analysis workflows, and real review access capabilities can effectively improve the structured expression and readability of e-commerce review analysis systems.

Keywords: large language model; e-commerce review analysis; multi-agent; task-oriented workflow; intelligent agent system

## 第一章 绪论

### 1.1 研究背景

用户在电商平台选购商品时,常常先看评论。问题也恰好出在这里。评论数量很多,表达方式很散,同一件商品里常常混着体验分享,情绪宣泄,物流抱怨,售后反馈和场景描述。用户想问的其实很直接: 这件商品值不值得买? 差评集中在哪些方面? 物流和售后到底有没有问题? 但是平台通常只给出评分,标签或简单排序,这些信息能提供线索,却很难直接支撑判断。

传统评论分析方法通常把重点放在情感分类,关键词统计或高频词提取上。研究者可以借助这些方法快速概览评论倾向,但是它们很难同时回答三个问题。第一,系统怎样获得真实评论数据。第二,系统怎样把评论转换成可量化指标。第三,系统怎样把指标和原始证据组织成用户能读懂的结论。也就是说,用户需要的不是一段空泛总结,而是一份带证据的分析结果。

大语言模型给这类任务带来了新的处理方式。它能理解自然语言问题,也能把分析过程拆成若干步骤。进一步看,当模型不再只生成一段回答,而是主动调用检索,统计和可视化等工具时,系统就从“会说话”走向了“会做事”。这正是 Agent 形态的价值所在。Agent 不只接收问题,它还会组织任务,调用外部能力,检查中间结果,最后再汇总输出。

但是,只把大语言模型接到聊天界面上还不够。用户问“帮我分析这款商品的差评”,系统如果既拿不到评论数据,也没有结构化统计能力,最后往往还是会退回模糊回答。还有一个更现实的问题: 评论分析往往不是单步任务。系统需要先识别商品,再准备数据,接着决定是否执行统计分析,是否召回评论证据,是否生成图表。任务组织和结果校验都不能依赖单轮生成,这正是本文要解决的问题。

基于上述背景,本文把研究对象限定为电商商品评论分析场景,并围绕当前项目的真实实现展开论述。该系统面向普通消费者,支持用户以自然语言和京东商品链接发起分析请求。后端不再把消息简单当作聊天文本处理,而是通过统一消息入口创建分析任务,再由多智能体工作流完成评论采集,统计分析,语义证据召回和结果汇总,最后把文本结论,图表配置和证据评论返回给前端工作台展示。这一实现路径直接对应项目现有文档和代码,不是概念性设想。

### 1.2 国内外相关研究

现有研究已经证明,大语言模型和智能体正在改变复杂任务的处理方式,但不同研究的关注重点并不相同。第一类研究把焦点放在 LLM 与 Agentic AI 的整体能力和风险上。这类工作指出,大语言模型具备语言理解与推理优势,Agent 系统则进一步把这些能力延伸到工具调用,任务执行和跨模块协作中。与此同时,安全性,可信性,透明性,上下文管理和人类监督等问题也会跟着进入系统设计过程。[参考文献占位: 1] 这类研究为本文提供了总背景,也提醒本文不能把“模型能回答”直接等同为“系统能可靠完成任务”。

第二类研究聚焦数据分析智能体或知识服务智能体。相关工作已经尝试让大语言模型把自然语言需求转成专业分析流程,再连接数据库,专业软件或知识服务模块来完成任务。例如,有研究通过模块化架构组织分析步骤,强调需求理解,指令生成和结果总结之间的衔接; 也有研究通过标准协议把模型和专业软件连接起来,从而提升复杂分析场景的自动化程度。这些研究说明,分析型智能体不能只依赖单轮生成,它更需要清晰的流程拆分和可调用工具。本文认同这一思路,但是没有采用 MCP 协议,也没有把 GIS 或军事数据分析中的实现方案直接照搬到电商评论场景。

第三类研究关注分层架构与多智能体协作。有研究提出五层或多层式分析 Agent 结构,把数据获取,知识组织,规则约束和应用层能力拆开处理; 也有研究通过多 Agent 协作框架来提升复杂推理任务的准确性,强调不同角色之间的分工与协同。这类研究对本文的启发很直接: 单一模型很难稳定承担数据准备,结构化分析,证据检索和最终审查这几类职责,所以系统更适合通过工作流把不同节点串起来。本文也沿用了这一思路,把任务分流,统计分析,语义检索,可视化生成,答案汇总和结果审查拆给不同环节处理。不过,本文没有使用知识图谱推理,也没有构建高度泛化的跨领域协作框架,而是围绕电商评论分析这个具体任务设计最小闭环。

第四类研究来自评论分析,情感分析和服务质量评价领域。相关研究指出,仅靠粗粒度情感正负分类,很难充分提炼评论中的价值信息。评论文本里往往同时包含设施体验,服务失误,物流反馈和极端满意或不满意的描述。研究者如果进一步分析评论维度,设施词,厌恶词或奖励词,就能更准确地定位问题和改进方向。[参考文献占位: 8] 还有研究通过预训练语言模型提升评论情感分析效果,说明评论理解本身需要更强的语义建模能力。在电商物流服务质量评价研究中,评论抓取,清洗和维度化分析也被证明具有现实价值。这些工作让本文明确了一点: 电商评论分析不能只停在情感标签层面,它需要把结构化指标和原始评论证据一起给用户。

把上述研究放在一起看,当前研究仍然存在一块缺口。已有工作要么重在通用 Agent 框架,要么重在领域问答,要么聚焦评论情感识别。真正把商品评论采集,任务化调度,结构化统计,语义证据召回,图表展示和前后端闭环整合到同一系统中的研究并不多见。本文的工作正是围绕这一缺口展开: 项目不追求抽象平台化能力,而是针对“用户如何通过自然语言快速判断商品是否值得购买”这一场景,给出一个有真实代码支撑的实现方案。

### 1.3 研究内容及目标

本文的研究对象是一个面向电商商品评论分析场景的 LLM 智能体系统。研究目标并不抽象。用户进入系统后,可以先登录,再创建或进入会话,随后输入自然语言问题和商品链接。系统接收到消息后,不会直接返回一段同步聊天回复,而是先写入消息,解析商品上下文,创建或复用分析任务,再由后端工作流继续推进评论准备,统计分析,语义检索和结果生成。最后,前端工作台展示任务进度,文本结论,图表配置和证据评论。这个目标来自项目现有实现,不是未来功能规划。

围绕这一目标,本文的研究内容主要包含五个方面。

第一,本文研究统一消息入口与会话机制。当前系统把用户提问统一接入会话消息入口。服务层先保存用户消息,再判断消息中是否包含商品链接,如果没有,系统就尝试复用当前会话已经绑定的商品信息,随后创建或复用分析任务。也就是说,系统不再采用“普通聊天链路”和“商品分析链路”并行的旧设计,而是把请求统一推进到任务化分析协议中。

第二,本文研究基于 LangGraph 的多智能体工作流。整个工作流先确认商品上下文是否可信,再检查评论数据和向量索引是否齐备。数据准备完成后,系统根据问题类型决定是否执行统计分析,语义检索和图表生成,随后汇总中间结果,最后再由审查环节决定是否直接通过或重新执行局部步骤。这一设计使系统能够处理多步骤分析任务,而不是把所有逻辑压在单次生成里。

第三,本文研究三层数据架构。系统把 MySQL 作为业务真相层,保存用户,商品,评论,会话,消息,任务和报告等主数据; 把 DuckDB 作为临时聚合分析层,承担轻量统计计算; 把 ChromaDB 作为语义检索层,支撑评论向量检索。这样做有两个直接好处。其一,商品评论按商品复用,不会因用户不同而重复存储。其二,任务记录与分析报告分别承担过程记录和结果持久化职责,边界清楚。

第四,本文研究真实评论采集与数据准备链路。系统当前接入了基于 DrissionPage 的京东评论爬虫。工作流在数据准备阶段按需触发采集,爬虫进入商品页,打开评论区域,监听评论接口并获取评论数据,随后由清洗模块做标准化处理,再把评论写入关系型数据库并执行向量化。这一实现让系统具备真实数据基础,避免只对静态样例进行分析。

第五,本文研究前后端协同的工作台式交互。后端采用 FastAPI 提供认证,会话和任务接口。前端采用 Vue 3,Pinia 和 Vue Router 构建单页工作台。前端不仅展示消息流,还负责任务轮询,结果缓存和分析结果渲染。也就是说,本文实现的不是一个只返回字符串答案的聊天页面,而是一个围绕任务状态和结构化结果组织的分析工作台。

基于上述研究内容,本文希望达到三个具体目标。其一,让用户能够以自然语言发起商品评论分析请求,降低传统评论筛选和比对的时间成本。其二,让系统输出同时包含量化指标和评论证据,提高分析结果的可读性与可验证性。其三,通过统一消息入口,任务化协议和多智能体工作流,构建一个真实可运行的工程闭环。需要说明的是,需求文档中提到的邮件推送分析报告功能当前尚未实现,所以本文不会把它写成既有成果,只会在后文的不足与改进方向中提及。

## 第二章 相关技术研究

### 2.1 LangGraph 多智能体编排框架

用户发来分析请求后,系统需要依次完成数据准备,任务分流,分析执行和结果收束等多个步骤。如果把这些动作都塞进一条提示词里,模型很容易把流程揉成一团,结果看起来像回答了,其实过程不可控。本文没有采用这种写法。系统把分析流程交给 LangGraph 编排,让工作流自己决定先后顺序,状态推进和节点跳转。

从实际设计看,系统先构建共享状态驱动的工作流图,再把商品上下文解析,数据准备,任务路由,统计分析,可视化生成,语义检索,答案汇总,结果审查和最终收束这些环节依次纳入同一条执行链。这里的关键不在“步骤多”,而在“职责拆开了”。系统先确认商品是否明确,再确认评论数据是否可用,然后才把任务分派给统计分析,语义检索和回答汇总模块。路由环节负责分流,结果审查环节负责最后把关。这样一来,每个环节只解决一种问题,工作流也就更容易维护。

引入状态流转框架的原因在于,本项目处理的不是静态问答,而是会变化的任务。任务刚创建时,系统只知道用户发来了一条消息。等商品上下文解析完成后,系统才知道这条消息里有没有合法商品。再往下走,数据准备环节会根据评论数据和向量索引状态决定是否需要补数。到了任务分流阶段,系统又要判断是否需要统计分析,是否需要语义检索,是否需要图表输出。可以看到,同一条请求在不同阶段拥有不同状态,所以系统需要一套显式的状态推进机制。

还有一个常被忽略的问题,也就是质量控制。工作流如果只管往前跑,中间结果就可能不完整。本文在答案汇总之后接入结果审查环节,就是为了在最终收束前做一次检查。审查环节可以决定直接通过,也可以要求统计分析,图表生成,语义检索或答案汇总中的某一部分重新执行。这个设计没有把“是否重试”交给人工判断,而是交给工作流内部机制处理,所以系统在面对复杂分析请求时更稳定。[参考文献占位: 7]

说到底,LangGraph 在本文里扮演的是流程编排层角色,不是模型本体。它不负责生成分析结论,它负责把任务送到正确节点,把中间状态保留下来,再把结果汇总成可继续处理的结构。正因为有这一层,系统才能把“用户提问”变成“可执行分析流程”,而不是停留在一次性生成答案的层面。

### 2.2 FastAPI 后端开发框架

后端框架首先要解决的是请求接入,任务调度和结果返回这三类基础问题。本文选择 FastAPI,原因很直接。它适合组织 REST 风格接口,也方便在同一个服务里管理应用生命周期,鉴权依赖和路由分组。对本项目来说,这比追求复杂框架能力更重要。

从系统结构看,后端在启动时会先完成数据库初始化,然后再加载认证,会话和分析任务三类接口模块。这样的分组方式跟业务边界是一致的。认证模块解决用户身份问题,会话模块处理统一消息入口和历史会话,分析任务模块处理进度查询,结果获取和失败重试。

FastAPI 在本文里承担的是接口壳层和服务接入层作用。它不直接完成评论分析,也不承担工作流编排。它做的事情更像交通枢纽: 用户请求先到接口层,接口层再把请求分发给会话服务或任务服务,最后把结果按统一协议返回前端。这样拆开之后,后端结构就很清楚。接口层负责收发,服务层负责业务,工作流层负责执行。

### 2.3 Vue 前端开发框架

本文的前端并不是一个简单的聊天输入框和回复框组合,而是一个围绕任务推进和结果展示构建的工作台。用户发出请求后,系统不会立刻返回最终结论,而是先返回任务标识,再逐步推进状态。所以前端必须能保存会话,轮询任务,缓存结果,还要把文本,图表和证据组织在同一个工作区里。本文选择 Vue 3,Pinia 和 Vue Router,就是为了支撑这种单页工作台形态。

前端应用在挂载前会先恢复登录状态。这个顺序不是细枝末节。用户刷新页面后,系统如果不先恢复认证信息,页面路由就无法准确判断该去登录页还是聊天工作台。当前前端只保留两个核心页面,也就是认证页和聊天工作台。路由守卫直接依据本地登录凭据控制访问权限,这样页面边界很清楚。

真正体现“工作台”特征的是前端状态管理层。这里不是简单保存消息数组,而是同时维护会话列表,当前会话详情,任务进度缓存,任务结果缓存和轮询状态。用户发送消息后,系统会先确保当前存在有效会话,然后发起消息请求,刷新会话详情,再启动任务轮询。任务完成后,前端再主动拉取结构化结果。也就是说,前端没有把分析结果当作一条普通文本,而是把它当作一个带状态,带缓存,带结构化字段的对象来处理。这样设计之后,聊天界面就不只是“问答窗口”,而是“会话管理 + 任务跟踪 + 报告展示”的复合工作台。

### 2.4 SQLAlchemy ORM 和数据库设计

系统一旦进入任务化分析阶段,后端就必须同时管理用户身份,会话归属,任务状态和报告结果。如果每次都手写底层 SQL 来拼接这些关系,开发成本会很高,错误也容易堆积。本文使用 SQLAlchemy ORM,就是为了把业务对象和数据表关系显式绑定起来,让服务层围绕对象读写数据。

数据库设计部分更加关键。系统把用户,商品和评论放在基础数据层,再把会话,消息,任务和报告组织成用户私有分析链路。这个划分解决了两个核心问题。第一,同一商品的评论数据不会因为多个用户重复抓取和重复入库。第二,系统把“任务过程”和“分析结果”拆成两类实体保存,前者记录状态推进,后者保存最终产物,边界不会混淆。

任务实体的设计尤其能体现本文的工程取向。任务记录不仅保存任务标识和执行状态,还保存当前阶段,进度百分比,触发来源以及起止时间。换句话说,系统没有把任务状态临时塞进内存变量里,而是把它持久化到了数据库。这样做的原因在于,前端需要轮询任务进度,失败任务也需要重试,这些能力都建立在可追踪,可恢复的任务状态之上。

报告实体则回答另一个问题: 最终结果以什么形式存在。当前设计把文本总结,统计结果,图表配置和证据摘要统一存入报告记录,并让它与任务记录形成一一对应关系。这样做之后,系统既能保留完整分析结果,也能在消息时间线里只显示摘要信息,两者互不冲突。对论文来说,这也是一个很值得强调的设计点。系统不是简单保存一段回答文本,而是保存一个结构化分析产物。


### 2.5 DuckDB 内存分析引擎与 ChromaDB 向量数据库

单一数据库很难同时兼顾业务真相存储,临时统计分析和语义检索这三类职责。理论上把这些工作都压给 MySQL 可以勉强运行一部分流程,但是效果不会好。因为 MySQL 擅长保存业务真相,不擅长承担灵活的临时统计分析和语义检索。所以本文没有让单一数据库包办全部分析任务,而是把统计分析和语义检索拆到 DuckDB 和 ChromaDB 上处理。

先看 DuckDB。本文把它当作轻量分析引擎使用,主要承接 SQL Agent 的聚合任务。评论一旦进入分析阶段,系统会围绕目标商品构造临时评论集合,再计算差评率,评分分布,维度分布等统计结果。这里需要的是快速聚合和临时计算,不是长期业务存储。所以 DuckDB 负责“算”,而 MySQL 负责“存”,两者分工明确。

再看 ChromaDB。语义检索这件事,单靠关系型条件过滤做不好。用户问“物流问题严重吗”,系统不能只按关键词机械匹配,它还要从大量评论中召回含义接近的证据片段。系统先把评论文本送到远程嵌入服务生成向量,再把评论原文和商品,评分,维度等元数据写入评论向量集合。查询时,系统对用户问题生成查询向量,按商品范围过滤后执行相似度检索,最后再返回去重后的证据评论。[参考文献占位: 4]

这套设计还有一个边界很重要,也就是“主数据在 MySQL,检索能力在 ChromaDB”。评论原文不是只保存在向量库里,它首先保存在 `comments` 表中。向量库只是基于这些主数据生成的检索副本。坚持这一点的原因在于,一旦检索层异常,系统至少还能保留业务真相和任务链路,不会因为向量索引问题直接丢失评论数据。

把 DuckDB 和 ChromaDB 放在一起看,它们其实分别解决了两类不同问题。DuckDB 让系统拿到可量化指标,比如数量,比例和分布。ChromaDB 让系统拿到语义证据,比如“用户到底在抱怨什么”。前者支撑统计结论,后者支撑文本解释。两者配合之后,系统才能既会算,也会找证据。对于电商评论分析来说,这正是比单纯聊天系统更有价值的地方。


### 2.6 本章小结

本章围绕系统实现所依赖的关键技术与核心支撑机制展开介绍,说明了为何在实际项目中采用 LangGraph, FastAPI, Vue, SQLAlchemy, MySQL, DuckDB 和 ChromaDB 共同完成任务化分析系统的前后端协同实现,也说明了工作流编排,接口组织,状态管理,关系型存储,统计分析与语义检索各自承担的职责。上述技术选择共同支撑了系统从用户提问到分析结果返回的完整链路,也为后续的系统设计,模块实现和测试分析奠定了基础。

## 第三章 总体设计

### 3.1 系统整体架构设计

本文面对的不是普通问答场景，而是要处理商品识别、评论准备、任务推进、结构化分析和结果展示的完整链路。系统在总体设计时按职责差异拆成前端展示层、接口层、服务协调层、工作流编排层、数据采集与分析层以及数据存储层六个部分。这种分层基于关注点分离原则，每层只处理职责域内问题，层间通过显式契约交互，降低系统认知复杂度与维护成本。
前端展示层直接面向用户，负责接收自然语言提问，展示历史会话，轮询任务状态，并将文本结论、图表和证据评论组织成可阅读的分析结果。其内置动态渲染机制，能根据后端返回的数据类型自动切换文本卡片、统计图表或证据列表的展示模式。接口层承担对外通信职责，接住认证、会话和任务请求后转交具体服务模块，不直接完成分析，同时集成限流与熔断策略，防止突发流量穿透下游核心服务。
系统中枢在服务协调层和工作流编排层。服务协调层负责识别商品上下文，创建或复用分析任务，调度执行过程，监控各阶段执行耗时与异常，结果完成后将摘要和完整报告分别回写。工作流编排层则把复杂任务拆成多阶段：先确认分析对象，再检查评论和向量数据是否充足，随后决定是否需要统计分析、语义检索和可视化生成，最后汇总并审查结果。两层通过共享状态对象传递上下文，确保任务全生命周期可追溯。系统并非"收到问题"立刻生成回答，而是"明确对象"后逐步推进分析流程。
数据采集与分析层承担执行能力，包含评论采集、清洗、向量化及统计计算、证据召回和图表生成。过程中，数据采集层、数据接入层、应用层均可调用模型与引擎层（DeepSeek大模型或相关服务）辅助数据处理和功能整合[5]。数据存储层采用多模态分区策略：结构化数据存入关系型数据库保证事务一致性，非结构化评论文本及向量表征存入专用检索引擎支持语义召回，元数据与索引集中管理。这种分层在用户交互、业务调度、分析执行和结果存储间建立清楚边界。
从设计思想看，本文架构强调三点：统一消息入口，不拆分"普通聊天"和"商品分析"两套主入口，统一进入会话消息处理；任务状态推进，将分析视为可追踪、可恢复的任务而非一次性生成；结构化结果返回，交付前端的不仅是自然语言，还包括图表配置、证据评论和过程上下文。这三点将系统从普通对话界面推向真正可用的分析工作台，并使其具备渐进式扩展潜力——新增分析维度或接入新平台时，只需在特定层内增改模块，无需触动整体架构稳定性。这种分层隔离与契约驱动的设计，既极大降低了模块间的耦合风险，也为后续持续集成与自动化测试提供了清晰的边界条件，使系统能够在业务迭代中保持结构韧性。

### 3.2 三层存储架构设计

系统设计到数据层时，首先需要解决存储职责分离问题。如果所有数据都压进同一存储组件，开发初期似乎更省事，但是后续问题会很快暴露出来。业务真相存储，临时统计分析和语义检索这三类任务关注点并不一样。把它们混在一起，系统很容易出现职责混乱，性能受限和数据边界不清的问题。所以本文采用了三层存储架构，分别由 MySQL， DuckDB 和 ChromaDB 承担不同职责。
MySQL 位于最底层，负责保存业务真相。用户账户，商品信息，评论数据，会话记录，消息内容，任务状态和分析报告都放在这一层。把它定义为业务真相层，是因为系统后续的任务轮询，失败重试，报告回溯和会话恢复都依赖稳定且可追踪的主数据。如果主数据不稳，上层分析能力再强也没有意义。
DuckDB 解决的是另一个问题，也就是临时统计分析。商品评论进入分析过程后，系统需要快速计算差评率，评分分布和维度统计等结果。这类计算强调轻量，灵活和面向任务，不强调长期持久化。所以系统把它们交给聚合分析层处理。这样做之后，关系型主库不用承担高频临时统计压力，分析逻辑也能保持相对独立。
ChromaDB 则服务于语义检索。用户问“物流问题严重吗”时，系统不能只返回一个比例数字，它还需要拿出几条真正能说明问题的评论证据。要完成这一步，系统必须先把评论文本转换成向量，再按商品范围执行相似度检索。语义检索层解决的正是这个问题。它并不保存业务真相，它保存的是面向检索的向量化副本和相关元数据。
三层存储架构还有一项关键原则，也就是评论按商品复用，不按用户重复存储。同一件商品被不同用户分析时，系统不会重复抓取和重复保存评论数据。系统只在用户链路层记录“谁在什么会话里发起了什么任务，又得到了什么结果”。这一点既降低了数据冗余，也让共享商品数据与用户私有链路数据之间形成了稳定边界。
把三层存储放在一起看，它们对应的是三种不同职责。MySQL 负责记住事实，DuckDB 负责计算指标，ChromaDB 负责找回证据。这样设计之后，系统既能保持数据的一致性，也能兼顾分析效率和检索能力。更重要的是，任务记录和报告记录也在这套架构中找到了明确位置。前者记录过程，后者保存产物，二者相互关联，却不相互替代。

### 3.3 多智能体协作架构设计

系统采用多智能体协作，而不是让一个模型一次性把结论生成出来，核心原因在于任务复杂度决定了可靠性上限。一次性生成的方式适合短问题，也适合低风险场景，但是在商品评论分析中，用户的问题往往同时包含对象识别，评论准备，统计分析，证据召回和结论组织等多个子任务。单一模型如果既要判断流程，又要调用能力，还要审查结果，很容易顾此失彼。
本文把协作架构拆成前置准备，任务分流，分析执行，结果汇总和结果审查五个部分。前置准备环节先处理两个问题。第一，用户到底在分析什么商品。第二，系统手上到底有没有可用评论数据。只有这两个问题都回答清楚，后续分析才有意义。也就是说，本文的多智能体工作流不是从“直接回答问题”开始，而是从“确认分析对象和分析条件”开始。
任务分流环节承担路线选择职责。用户有时只需要简短判断，有时则会要求差评统计，维度分析和证据解释同时给出。系统在这一环节判断下游到底需要哪些分析能力参与，而不是让所有模块机械执行一遍。这样既减少了无效调用，不同问题能够匹配不同分析深度。
分析执行环节由三个核心能力组成。第一类能力负责结构化统计，它从评论数据中计算数量，比例和分布等指标。第二类能力负责语义检索，它从评论语料中召回可以支撑结论的证据片段。第三类能力负责图表生成，它把统计结果转成前端可渲染的可视化配置。这三类能力各自解决不同问题，但最终都指向同一个目标，也就是让系统既能给出概括，也能给出依据。
结果汇总环节负责把前面的中间结果组织成面向用户的分析回答。它不是简单拼接文本，而是要把结构化指标，评论证据和图表信息协调起来，让回答既完整，又可读。但是汇总完成后，系统并不会立刻结束。结果审查环节会继续判断当前输出是否足够支撑用户提问，并检查是否遗漏了必要信息。如果发现结果不完整，系统会要求相关分析步骤重新执行。这样的设计把质量控制放进了工作流内部，而不是留给人工兜底。
从总体上看，多智能体协作架构体现的是“分而治之，再统一收束”的设计思路。系统没有让任何一个单元独自承担全部分析责任，而是让不同环节各司其职，再通过工作流把它们串起来。这样做不仅提高了任务可解释性，也为后续扩展新的分析能力留下了空间。将来如果系统接入新的分析节点，只要把它纳入现有工作流边界中，整体架构仍然能够保持稳定。

### 3.4 数据库设计与 E-R 图

数据库设计不只是把几张表连起来，它更重要的是说明系统中的角色关系和数据边界。本文在数据库设计中围绕这些关系构建了用户，商品，评论，会话，消息，任务和报告七类核心实体。
用户实体描述系统使用者，会话实体描述用户交互空间，消息实体记录用户与系统之间的时间线。商品实体和评论实体构成共享商品数据层，它们面向的是商品对象本身，而不是某个具体用户。任务实体记录用户针对某件商品发起的一次分析过程，报告实体则保存这次分析的最终产物。换句话说，一个实体负责记录“怎么分析”，另一个实体负责记录“分析出了什么”。
在实体关系上，用户与会话是一对多关系，会话与消息也是一对多关系。商品与评论同样是一对多关系，因为一件商品通常包含多条评论。任务实体与消息实体之间建立触发关系，也就是一条用户消息触发一次分析任务。任务实体与报告实体之间则形成一对一关系，表示一次分析任务默认产出一份分析报告。这样的关系设计让系统能够从用户提问一路追溯到分析过程和最终结果，链路是闭合的。
数据库设计还体现了一项明确边界：商品数据共享，用户链路私有。商品和评论不按用户重复保存，会话，消息，任务和报告才跟具体用户绑定。这一划分既能减少冗余存储，也方便多个用户复用同一商品的评论基础数据。对于本文这样的分析系统而言，这不是细节优化，而是支撑整体架构稳定运行的重要前提。

## 第四章 系统需求分析

### 4.1 系统描述

本文面向的不是企业级运营后台，也不是面向分析师的专业数据平台，而是一个服务普通消费者的商品分析辅助系统。用户进入系统后，希望用尽量低的操作成本完成一件事，也就是借助自然语言提问和商品链接输入，快速判断某件商品是否值得购买。系统围绕这一目标组织交互流程，把复杂的数据准备和分析过程隐藏在后端任务链路中，把用户真正关心的内容集中呈现在工作台界面上。
从输入形式看，系统当前支持两类核心输入。第一类输入是自然语言问题，例如用户希望系统重点分析差评，物流，售后或质量等维度。第二类输入是商品链接。系统收到这两类输入后，会先确定分析对象，再判断后续是否需要补充评论数据和向量索引。这样设计的目的不是增加使用门槛，而是让后续分析建立在明确对象之上，避免出现“问题明确但分析对象不明确”的情况。
从输出形式看，系统不把结果压缩成一段简单回复。它会先反馈任务状态，让用户知道分析是否已经启动，当前推进到哪个阶段，是否需要继续等待。任务完成后，系统再返回文本结论，图表信息和评论证据。文本结论负责概括主要判断，图表负责展示结构化分布，证据评论负责支撑结论来源。这三类输出共同构成了系统的结果呈现方式。
从应用范围看，系统当前聚焦京东商品评论分析场景。商品数据来源，评论采集方式和后续数据准备逻辑都围绕这一平台展开。这样的限定并不意味着系统不能扩展，而是说明本文当前讨论的需求边界是清楚的。系统首先解决的是单平台，单场景下的分析闭环问题，而不是在研究阶段就把多平台接入目标全部摊开。

### 4.2 功能性需求分析

系统的功能性需求可以分成五类。第一类需求是用户认证与会话管理。系统需要支持用户注册，登录和身份校验，也需要支持会话创建，切换，重命名和删除。为什么这部分不能省略？因为系统要保存用户的历史分析过程，会话既是交互容器，也是任务和结果的组织单位。如果没有稳定的用户和会话机制，分析结果就无法形成连续的使用链路。
第二类需求是商品上下文识别与消息接入。用户发来消息时，系统需要先保存消息，再识别其中是否包含有效商品链接。如果用户没有重复贴出链接，系统还需要能够复用当前会话已经绑定的商品信息。输入是用户问题和可能出现的商品链接，处理是商品对象确认与消息入库，输出则是可以继续推进的分析任务。这里必须强调一点，当前系统的真实入口是统一消息入口，不是“普通聊天”和“商品分析”两套并行入口。
第三类需求是评论数据采集与准备。商品对象确定后，系统需要判断评论数据是否足够，向量检索条件是否具备。如果数据不足，系统就要触发评论采集，清洗，入库和向量化流程。输入是商品对象和现有数据状态，处理是评论补充与索引准备，输出是可供后续分析使用的评论数据集。没有这一层，统计分析和语义检索都无法稳定展开。
第四类需求是多阶段分析与结果生成。系统需要围绕用户问题自动决定是否执行统计分析，是否进行语义检索，是否生成图表，最后再把这些中间结果汇总成可直接展示的分析结论。输入是用户问题，商品对象和评论数据，处理是任务分流，统计计算，证据召回，结果汇总与审查，输出是文本结论，图表配置和证据评论。对用户而言，这一类需求决定了系统是否真的具有“分析”能力，而不是只会复述评论内容。
第五类需求是前端展示与任务轮询。用户提交问题后，系统不能让页面长时间停留在静默状态。它需要在任务执行期间持续反馈进度，并在任务完成后展示结构化结果。输入是任务标识和任务状态变化，处理是前端轮询，缓存更新和结果渲染，输出则是任务进度视图和分析结果视图。这样设计的原因很实际，也就是让用户知道系统正在做什么，而不是只看到一个空白等待过程。
在功能边界上，还需要明确一点。需求文档中提到的分析报告邮件推送属于扩展功能，当前并未实现，所以不能把它纳入已完成功能需求中描述。本文讨论的功能性需求，必须严格限定在已经落地的认证，会话，任务，采集，分析和展示这些能力范围内。

### 4.3 非功能性需求分析

系统的非功能性需求主要体现在易用性，可维护性，可扩展性和可靠性四个方面。先看易用性。本文面向的用户并不是专业数据分析人员，所以系统必须尽量降低输入门槛。自然语言提问，商品链接输入，任务进度提示和结构化结果展示，都是围绕“让普通用户看得懂，也用得起”这一目标展开的。界面如果只给出技术术语或原始数据，系统就很难真正发挥辅助决策作用。
可维护性则更多体现在系统结构上。前后端分离使界面展示和后端服务能够独立演进，模块化服务让消息处理，任务调度，评论采集和向量检索可以分别维护，多阶段工作流又让不同分析环节的职责保持清楚。这样的结构能够减少后期修改时的牵连范围，也方便开发者定位问题来源。
可扩展性是本文必须考虑的一项要求。虽然当前系统主要面向京东商品评论分析，但是整体设计已经预留了扩展空间。新的商品平台可以通过增加采集模块接入，新的分析能力可以通过增加工作流节点接入，新的图表模板也可以通过前端组件和结果协议继续扩展。也就是说，系统当前实现的是一个最小可用闭环，但它的结构并没有把后续扩展直接锁死。
可靠性和安全性同样重要。系统需要通过用户鉴权保护会话数据，也需要通过任务状态持久化保障分析过程可追踪。任务执行失败时，系统还要能够记录错误信息并支持重试。对于一个任务型分析系统来说，可靠性并不只等于“服务能启动”，它更体现在任务能不能稳定推进，结果能不能被正确回收，失败后能不能继续恢复。

### 4.4 可行性分析

从技术可行性看，本文采用的技术组合已经能够支撑系统形成闭环。前端工作台负责交互与展示，后端接口负责接入与调度，工作流负责任务拆分与状态推进，关系型数据库负责业务真相持久化，聚合分析层和语义检索层分别承担指标计算与证据召回。这些组件不是分散堆砌，而是围绕同一条分析主链组织起来，所以技术路线具备现实落地基础。其中，工作流对复杂任务的拆解能力直接受益于链式思维（Chain-of-Thought）提示与相关推理技巧使 LLMs 能生成中间推理步骤、改进多步逻辑推理与任务规划，这为把模糊的自然语言意图分解为可执行子步骤提供了可操作的技术路径[6]。
从业务可行性看，商品评论分析本身具有明确价值。用户在购买前通常需要判断商品优缺点，尤其关注差评集中点，物流体验和售后表现。平台原生页面虽然提供了评论和评分，但是缺少自动归纳，证据提炼和结构化展示能力。系统把这些能力整合起来后，能够直接服务真实决策场景，所以业务需求是明确存在的。
从实现可行性看，本文并不是停留在概念设计阶段。系统已经具备真实前端页面，真实后端接口，真实任务链路和真实评论采集能力。用户可以完成登录，进入会话，发起分析任务，查看任务进度并获取结构化结果。换句话说，本文讨论的不是一个尚未实现的设想系统，而是一个已经形成基本闭环的分析系统。正因为存在真实实现基础，后续的需求分析才具有实际对应对象，不会停留在抽象描述层面。

### 4.5 用户用例分析

本文的核心用例可以概括为一条主业务流程。用户首先登录系统，随后创建新会话或进入既有会话，然后输入商品链接和自然语言问题。系统接收消息后，先识别商品对象，再创建分析任务并反馈任务状态。任务推进完成后，用户在工作台中查看文本结论，图表结果和评论证据。这条链路覆盖了从输入到输出的完整使用过程，也是系统设计和实现始终围绕的核心用例。
在这一主用例之外，系统还存在一条异常处理用例。当商品评论数据不足，评论抓取失败或后续分析过程出现异常时，系统不会直接中断整个使用过程，而是通过任务状态反馈错误信息，保留失败原因，并在满足条件时支持重新执行。异常用例的存在说明系统不是只考虑“理想流程能不能跑通”，还考虑了任务型系统在真实运行中如何面对不稳定情况。

## 第五章 核心模块实现

### 5.1 数据采集与清洗模块

数据采集模块解决的是分析链路中的起点问题。用户提出分析请求之后,系统如果没有真实评论数据,后续的统计分析和证据检索就没有可靠基础。所以本文没有采用静态样例数据来模拟分析过程,而是把评论采集模块接入到实际任务流程中,让系统在数据不足时自动补充评论数据。

当前实现围绕京东商品评论展开。系统首先根据用户输入或会话绑定信息确定目标商品,随后进入数据准备阶段。这里的判断很关键。如果系统发现评论数据已经存在且仍然可用,就直接进入后续分析; 如果数据为空或者已经过期,系统才触发评论采集。这样做的好处很直接,一方面避免重复抓取,另一方面也能保证评论数据具有基本时效性。

在具体执行过程中,采集模块会先进入商品页面,再进入评论区域,随后监听评论接口返回的数据包。评论获取之后,系统并不会直接把原始结果交给后续模块使用,而是先完成清洗与规范化处理。清洗阶段会去掉冗余信息,统一文本格式,提取评分和评论时间等结构化字段,并尝试识别评论维度。只有在数据完成这一轮处理之后,系统才会把评论写入关系型存储,并继续推进向量化流程。

这样设计的意义并不只是“把评论抓下来”。它更重要的价值在于,系统通过统一的数据准备过程,把原本零散的网页评论转成了可以参与统计分析和语义检索的标准化评论集合。对于电商评论分析场景而言,在线评论本身就是服务质量判断的重要依据,系统把这一依据稳定接入分析链路之后,后续的自动化分析才具备现实意义。[参考文献占位: 10]

### 5.2 多智能体工作流实现

如果把第五章看作系统真正开始运转的部分,那么多智能体工作流就是其中的核心驱动机制。任务创建之后,系统不会直接进入某一个固定分析步骤,而是先通过工作流判断当前任务应该如何推进。也就是说,工作流在这里承担的不是“补充功能”,而是“组织执行秩序”的核心职责。

整个实现过程可以概括为四个连续阶段。第一阶段是商品上下文确认。系统需要先判断当前任务到底在分析哪件商品,商品信息来自消息中的链接,还是来自会话已经绑定的对象。第二阶段是数据准备。系统在这一阶段检查评论数据和向量索引是否齐备,必要时触发评论采集和向量化补全。第三阶段是分析执行。系统根据问题内容决定是否调用统计分析能力,语义检索能力和图表生成能力。第四阶段是结果收束。系统在汇总中间结果之后,继续执行结果审查,确认当前输出是否已经覆盖用户关心的问题。

这种实现方式和一次性生成存在明显差异。一次性生成把任务理解,分析执行和结果判断都压在同一次输出里,所以系统很难解释自己为什么这样回答,也很难在结果不完整时只重做局部步骤。本文的工作流实现则把这些动作拆成前后衔接的阶段。这样一来,任务执行顺序能够被明确追踪,中间状态能够被持续记录,局部结果不足时也能回到对应环节重新执行。

结果审查环节在这一章尤其值得强调。系统并没有把第一次汇总结果直接交给前端,而是增加了一次质量检查。这个检查并不负责重新做完整分析,它负责判断当前结果是否遗漏关键信息,并在必要时要求局部能力重新执行。对于分析型智能体来说,这种“从需求理解到结果总结再到质量复核”的闭环设计,比单次输出更适合处理复杂问题。[参考文献占位: 5]

### 5.3 数据分析与检索模块

在评论数据准备完成后,系统接下来要解决的是“怎么算”和“怎样找证据”这两个问题。前者对应统计分析,后者对应语义检索。两者缺一不可。只有统计结果,系统容易显得结论空泛; 只有评论证据,系统又很难给出稳定的总体判断。所以本文把数据分析与检索模块设计成相互配合的两条能力链。

统计分析链负责把评论集合转换成可量化指标。系统会围绕目标商品计算差评率,评分分布和维度分布等结构化结果。这样做的目的是把“评论很多,看不完”的原始状态转成“问题集中在哪些维度,比例大概是多少”的总结状态。用户面对这些统计结果时,能够更快把握商品整体评价。

语义检索链则负责补上“证据”这一层。统计指标可以告诉用户问题是否明显,但它不能替代原始评论本身。系统因此会根据用户问题构造检索请求,再从评论向量集合中召回含义接近的评论片段。召回结果经过去重和筛选之后,最终形成若干条可以直接支撑分析结论的证据评论。这样一来,系统输出的结论就不只是概括判断,还能够给出相应依据。

图表生成能力进一步把统计结果转成可视化信息。它本身不负责重新计算指标,而是把已有的结构化结果转换成前端可渲染的图表配置。文本解释,统计指标和证据评论经过这一轮整合之后,系统才能真正形成较完整的分析结果。评论文本分析研究已经证明,更强的语义建模能力能够改善复杂评论理解效果,这也说明本文将结构化分析与语义检索结合起来是有必要的。[参考文献占位: 9]

### 5.4 后端 API 设计与实现

系统在实现层面还需要解决一个经常被忽略的问题,也就是前端和后端怎样协作。本文没有采用“发送一次请求,同步返回最终结论”的方式,而是把接口设计成任务化分析协议。这样做的原因在于,评论采集,数据准备和多阶段分析都需要时间,如果接口仍然坚持同步直返,系统很难兼顾稳定性和可用性。

当前后端接口可以概括为三组。第一组是认证接口,负责用户注册,登录和身份确认。第二组是会话接口,负责会话创建,会话详情读取,消息发送和历史任务列表查询。第三组是任务接口,负责任务进度查询,结果获取和失败任务重试。三组接口分别对应用户进入系统,用户发起分析和用户查看任务结果这三类关键行为。

在交互流程上,系统采用三段式协议。用户发送消息后,后端先保存消息并创建或复用分析任务,随后立即把任务标识和初始状态返回给前端。接着,前端进入任务轮询阶段,持续查询任务当前进度和执行步骤。等任务完成后,前端再单独请求分析结果,获取文本结论,图表信息和证据评论。这样设计之后,前端能够清楚感知任务状态,后端也能够把复杂分析过程稳定拆分开来。

从实现效果看,这种接口设计把消息接入,任务推进和结果返回明确分开了。消息发送负责启动流程,进度查询负责反馈过程,结果接口负责交付产物,重试接口则为失败场景提供恢复能力。接口设计之所以写成这样,不是为了追求形式复杂,而是为了适应任务化分析系统本身的执行节奏。

### 5.5 前端交互界面设计

前端界面的实现没有停留在普通聊天窗口层面。系统把前端设计成一个工作台,目的在于把会话管理,任务跟踪和结果展示统一到同一交互空间里。用户进入聊天工作区之后,左侧可以管理历史会话,中间区域承载消息流和分析结果,底部输入区域负责接收新的自然语言问题和商品链接。这种布局使用户既能回看历史分析过程,也能在当前会话中继续追问。

任务状态在前端界面中占据很重要的位置。用户发送消息后,系统不会直接展示一个完整回答,而是先反馈任务启动情况,再逐步刷新当前阶段和执行进度。当前端感知到任务完成后,界面继续拉取并渲染结构化结果。这样一来,用户看到的不是一个突然跳出的结论,而是一个逐步推进的分析过程。

分析结果展示同样体现了工作台思路。系统不会把所有内容都压缩在一条文本气泡里,而是把文本结论,图表结果和证据评论组合成结果块显示。文本部分负责概括,图表部分负责呈现结构分布,证据评论负责增强可信度。用户在同一页面里就能完成“看结论,看图表,看依据”三个动作,不需要来回切换不同页面或不同模块。

从实现角度看,前端界面设计和后端任务协议是紧密耦合的。前端之所以能稳定显示进度和结果,依赖的是任务状态缓存,结果缓存和轮询机制共同配合。也正因为前后端在这一点上采用了一致的任务化思路,系统最终才能呈现出聊天式交互和分析式展示相结合的工作台体验。

### 5.6 本章小结

本章围绕系统从消息接入到结果展示的核心实现链路展开说明,介绍了评论采集与清洗,多智能体工作流,数据分析与检索,后端任务化接口以及前端工作台交互等关键模块的实现思路与协同关系。上述模块共同构成了系统的运行闭环,使电商评论分析任务能够从用户输入稳定推进到结构化结果返回,也为后续的系统测试与效果评估提供了实现基础。

### 6.3 模型测试对比

模型测试围绕回答完整性,统计解释准确性,证据一致性和整体稳定性展开。对本系统来说,模型是否能够在同一任务链路下稳定输出与统计结果和评论证据相互吻合的分析结论,比单纯生成更长文本更重要。[参考文献占位: 11]

当前测试结果表明,DeepSeek-V3.2 和 Qwen3.5-397B-A17B 的整体表现较好,两者在分析结论完整性,证据组织和任务适配性方面都达到了较高水平,综合评价为优。Kimi-K2.6 的整体表现处于中等水平,能够完成基本分析任务,但在结论稳定性和细节覆盖上仍有提升空间。Qwen3.5-4B 的表现相对较弱,在复杂评论分析场景下更容易出现信息遗漏或解释不充分的问题,综合评价为低。

从这组结果可以看出,参数规模更大,综合能力更强的模型在本系统中通常更适合承担多阶段分析任务。它们在处理统计结果,评论证据和最终回答之间的衔接时更稳定,输出质量也更容易满足系统对结构化分析结果的要求。这一结果也说明,模型选择会直接影响电商评论分析系统的最终表现,后续若继续优化系统效果,模型能力仍然是需要重点考虑的因素。

### 6.4 系统不足与改进方向

系统测试也暴露出当前实现边界。首先,评论采集能力目前主要围绕京东商品展开,平台覆盖范围还不够宽,系统距离通用电商评论分析工具仍有差距。其次,评论抓取仍然依赖真实页面结构和平台访问策略,一旦页面布局变化或访问限制收紧,采集链路的稳定性就会受到影响。这一点说明系统虽然已经具备真实评论接入能力,但在鲁棒性上还有继续完善的空间。

从模型测试结果看,当前系统已经能够区分不同模型在分析任务中的表现差异,但这并不意味着模型选择问题已经彻底解决。较强模型虽然能够提供更完整也更稳定的分析结果,可它们通常也伴随更高的资源消耗和调用成本。较弱模型虽然部署门槛更低,但在复杂评论分析场景下又更容易出现信息遗漏和解释不充分的问题。所以后续系统优化不能只看“能不能跑通”,还要继续在效果,成本和稳定性之间寻找更合适的平衡点。除此之外,需求分析中提到的报告邮件推送功能也还没有落地,当前结果交付仍然以工作台内查看为主。这意味着系统已经能够支持任务化分析和结构化展示,但在结果分发和持续服务能力上仍然偏基础。

后续改进更适合沿着三个方向推进。第一,扩展更多电商平台的数据接入能力,把当前单平台分析逐步拓展为多平台评论分析。第二,继续完善模型评估流程,在现有测试结论基础上补充更细粒度的样本对照和长期稳定性验证,让模型选择更有依据。第三,继续提升采集链路和结果服务的稳定性,并在工作台之外补充更灵活的报告分发方式。这样一来,系统才能从当前的可用原型进一步走向更稳健的实际应用。

本文围绕电商商品评论分析这一具体场景,完成了一个基于大语言模型的智能分析系统设计与实现。系统没有停留在单轮问答层面,而是把用户输入,商品识别,评论数据准备,统计分析,证据检索,图表生成和结果回收组织成一条可运行的任务链路。围绕这条主链路,本文完成了前后端分离工作台,任务化接口协议,多智能体协作流程,三层数据存储结构和真实评论采集能力的整合,使系统能够围绕商品评论给出文本结论,图表信息和评论证据相结合的分析结果。

从实现效果看,本文工作的价值主要体现在两个方面。一方面,系统已经形成了较完整的工程闭环。用户可以登录系统,进入会话,提交商品链接和自然语言问题,再通过任务进度查看分析推进过程,最后获得结构化结果。另一方面,系统在分析过程中没有把所有判断都交给一次性生成,而是通过任务分流,统计分析,语义检索和结果审查等环节逐步完成处理。这种实现方式让分析结果更容易被追踪,也更适合电商评论这类需要同时兼顾数据指标和文本证据的任务。
