# API 接口定义

> 基础路径：`http://localhost:8000`  
> 所有需要认证的接口都应携带：`Authorization: Bearer <token>`  
> 前端统一通过消息接口发起用户输入，分析任务由后端自动创建

---

## 1. 设计原则

1. 前端只有一个发送消息入口，不再单独调用“发起分析任务”接口。
2. 后端收到消息后自动判定是普通回复还是商品分析。
3. 商品分析类消息会派生 `analysis_task`，前端通过任务接口查询进度和结果。
4. `product_id` 默认表示 MySQL 内部商品主键。
5. 平台商品 ID 使用 `external_product_id` 表示，避免和内部主键混淆。

### 3.4 发送消息（统一消息入口）

| 项目 | 内容 |
|------|------|
| Method | `POST` |
| URL | `/api/conversations/{conversation_id}/messages` |
| 认证 | 需要 |

**请求体**
```json
{
  "content": "https://item.jd.com/100197744867.html 这个商品值不值得买？"
}
```

**处理规则**
- 后端先保存用户消息。
- 后端按“规则优先、模型兜底”判定消息类型。
- 如果是普通聊天，直接返回 assistant 回复。
- 如果是商品分析，自动创建 `analysis_task`，并返回任务信息。

#### 情况 A：普通聊天，响应 200

```json
{
  "code": 200,
  "data": {
    "handling_mode": "direct_reply",
    "user_message": {
      "id": 6001,
      "role": "user",
      "message_type": "chat",
      "content": "帮我总结一下刚才的结论",
      "created_at": "2026-04-12T09:20:00"
    },
    "assistant_message": {
      "id": 6002,
      "role": "assistant",
      "message_type": "chat",
      "content": "刚才的结论是：该商品质量尚可，但物流和售后反馈较弱。",
      "created_at": "2026-04-12T09:20:02"
    }
  },
  "message": "Reply generated successfully"
}
```

#### 情况 B：创建分析任务，响应 202

```json
{
  "code": 202,
  "data": {
    "handling_mode": "task_created",
    "user_message": {
      "id": 6003,
      "role": "user",
      "message_type": "analysis_request",

      "created_at": "2026-04-12T09:22:00"
    },
    "analysis_task": {
      "task_id": "task_9f4b2c71",
      "status": "pending",
      "current_step": "queued",
      "progress": 0
    }
  },
  "message": "Analysis task created"
}
```

## 4. 分析任务模块 `/api/analysis/tasks`

说明：
- 分析任务不再由前端显式创建。
- `POST /api/conversations/{conversation_id}/messages` 在命中分析意图时自动创建任务。
- 分析模块只负责查询任务状态和获取结果。

|------|------|
| Method | `GET` |
| URL | `/api/analysis/tasks/{task_id}` |

{

  "data": {
    "task_id": "task_9f4b2c71",
    "status": "processing",
    "current_step": "rag_agent",

      {

      {
        "step": "crawl_check",
        "label": "数据检查",
        "status": "completed"
      },
      {
        "step": "rag_agent",
        "label": "语义检索",
        "status": "processing"

## 6. 统一响应格式

### 6.1 成功响应

```json
{
  "code": 200,
  "data": {},
  "message": "success"
}
```

### 6.2 错误响应

```json
{
  "code": 400,
  "data": null,
  "message": "Invalid request"
}
```

### 6.3 常见状态码

| 状态码 | 说明 |
|--------|------|
| `200` | 成功 |
| `201` | 创建成功 |
| `202` | 已接受，后台处理中 |
| `400` | 请求错误 |
| `401` | 未认证 |
| `403` | 无权限 |
| `404` | 资源不存在 |
| `409` | 状态冲突 |
| `500` | 服务器错误 |

## 7. 调用流程示例

### 场景 A：普通聊天

```text
1. 用户登录
   POST /api/auth/login
2. 创建对话
   POST /api/conversations
3. 发送普通消息
   POST /api/conversations/{id}/messages
4. 后端直接返回 assistant 回复
```

### 场景 B：商品分析

```text
1. 用户登录
   POST /api/auth/login
2. 创建对话
   POST /api/conversations
3. 发送带商品链接的分析消息
   POST /api/conversations/{id}/messages
4. 后端返回 202，并附带 task_id
5. 前端轮询任务状态
   GET /api/analysis/tasks/{task_id}
6. 任务完成后拉取分析结果
   GET /api/analysis/tasks/{task_id}/result
7. 如需推送邮件
   POST /api/reports/{report_id}/email
```

---

## 8. 关键变更说明

1. 移除 `POST /api/analysis/start`，因为分析任务由消息接口自动创建。
2. 保留统一消息入口，避免前端承担业务判定职责。
3. 分析接口只负责“查任务”和“取结果”。
4. 响应中明确区分内部 `product_id` 和平台 `external_product_id`。
