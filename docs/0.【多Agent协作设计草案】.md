# 0.【多Agent协作设计草案】

## 1. 设计目标

当前后端分析链路已经具备统一消息入口、任务化执行、爬虫采集、统计聚合、向量检索和工作流编排能力，但整体仍偏向固定流水线，尚未形成真正由大模型驱动的多 Agent 协作。

本次重构目标是：

1. 将当前固定串行分析流程升级为真正的多 Agent 协作工作流。
2. 由 `router_agent` 基于用户问题动态决定后续需要启用的分析 Agent。
3. 将统计分析、评论语义分析、可视化生成、最终审查解耦为独立职责模块。
4. 保持现有任务化执行模式不变，继续以 `analysis_task` 作为异步分析任务载体。
5. 为后续代码实现提供可直接落地的节点划分、状态结构与输入输出协议草案。

---

## 2. 重构后的总体思路

新的后端分析链路不再是“写死顺序的分析流水线”，而是“由路由 Agent 决定下游能力组合”的多 Agent 协作模式。

推荐总流程如下：

1. 接收用户消息。
2. 解析商品上下文。
3. 检查商品数据是否需要重新采集。
4. `router_agent` 判断问题意图以及后续需要启用哪些 Agent。
5. 按需执行：
   - `sql_agent`
   - `visual_agent`
   - `rag_agent`
6. `answer_agent` 汇总各模块结果，生成候选回答。
7. `master_agent` 做最终审查。
8. 审查通过则输出给前端；不通过则按规则局部重试。

推荐工作流结构：

```text
receive_message
  -> resolve_product_context
  -> ensure_product_data
  -> router_agent
  -> [conditional dispatch]
      ├─ sql_agent
      │    └─ [if need_visual] -> visual_agent
      ├─ rag_agent
      └─ skip
  -> answer_agent
  -> master_agent
  -> [conditional]
      ├─ finalize
      └─ retry_dispatch -> rerun subset agents -> answer_agent -> master_agent
```

## 3. 各 Agent / 节点职责设计

### 3.1 `resolve_product_context`

该阶段属于数据准备节点，不一定由大模型驱动，主要负责商品上下文解析。

职责：
- 从当前消息中通过正则提取商品链接。
- 若提取到链接，则解析 `source + external_product_id`。
- 若未提取到链接，则尝试使用当前会话已绑定商品 `bound_product_id`。
- 若两者都不存在，则标记当前请求缺少商品上下文。

建议输出：

```json
{
  "product_context": {
    "has_product": true,
    "source": "jd",
    "external_product_id": "123456",
    "product_id": 88,
    "resolved_from": "message_link"
  }
}
```

或：

```json
{
  "product_context": {
    "has_product": false,
    "resolved_from": "none"
  }
}
```

---

### 3.2 `ensure_product_data`

该阶段属于数据采集与缓存检查节点。

职责：
- 若存在商品上下文，则查询该商品最近 3 天是否执行过爬虫。
- 若 3 天内已执行过爬虫，则跳过采集，直接复用现有数据。
- 若未执行过爬虫或数据过期，则触发爬虫采集并入库。
- 评论数据准备完成后，执行向量化并写入 ChromaDB。

建议输出：

```json
{
  "data_context": {
    "data_ready": true,
    "used_cache": true,
    "crawler_triggered": false,
    "vector_ready": true,
    "last_crawled_at": "2026-04-15T10:30:00Z"
  }
}
```

---

### 3.3 `router_agent`

这是多 Agent 工作流的核心入口，必须接入大模型。

职责：
- 判断后续是否需要统计分析。
- 判断是否需要评论语义检索。
- 判断是否需要可视化绘图。
- 只输出后续需要启用的 Agent，不负责指定统计目标。
- 当未绑定商品时，不阻断链路，而是关闭依赖商品数据的 Agent，由 `answer_agent` 在末端统一回答。

典型示例：
- “分析商品的评分情况” → 需要 SQL，不一定需要可视化。
- “分析商品的评分并可视化” → 需要 SQL + 可视化。
- “商品的差评率是多少？” → 需要 SQL，不需要可视化。
- “商品的差评分布” → 需要 SQL，通常需要可视化。
- “帮我推荐下一步怎么分析” 且当前未绑定商品 → 不启动 SQL/RAG/可视化，由 `answer_agent` 直接回答。

建议系统提示词核心要求：
- 你是商品分析任务路由专家。
- 你需要根据用户问题决定是否调用 `sql_agent`、`rag_agent`、`visual_agent`。
- 若当前没有商品上下文，不要分配依赖商品数据的任务。
- 输出必须为严格 JSON。

建议输出：

```json
{
  "route_decision": {
    "need_sql": true,
    "need_rag": true,
    "need_visual": true,
    "response_style": "professional_analysis",
    "reason": "用户要求分析差评分布并可视化，需要统计、图表与评论语义解释。"
  }
}
```

---

### 3.4 `sql_agent`

该 Agent 必须接入大模型，但不直接开放任意 SQL 生成功能，而应基于“受控 SQL 工具”完成统计分析。

职责：
- 直接根据用户问题自主识别统计任务。
- 选择合适的 SQL 工具函数。
- 调用统计工具获取结构化指标。
- 输出统计值与对统计结果的简要解释。

当前实现约束：
- `router_agent` 只负责决定是否启用 `sql_agent`，不再向它传递 `analysis_targets`。
- `sql_agent` 需要自行从用户问题判断本轮该调用哪些受控统计工具。
- 若大模型规划工具失败，直接返回空统计结果，不再使用本地确定性兜底。
- 若统计摘要生成失败，直接返回空统计结果，不再使用本地描述模板。

建议首批 SQL 工具：
- `get_score_summary(product_id)`
- `get_score_distribution(product_id)`
- `get_bad_review_rate(product_id)`
- `get_bad_review_distribution(product_id)`
- `get_dimension_stats(product_id)`
- `get_dimension_detail(product_id, dimension)`
- `get_top_negative_dimensions(product_id)`
- `get_comment_volume_trend(product_id)`

建议输出：

```json
{
  "sql_result": {
    "tool_calls": [
      {
        "tool": "get_bad_review_rate",
        "args": { "product_id": 88 }
      },
      {
        "tool": "get_bad_review_distribution",
        "args": { "product_id": 88 }
      }
    ],
    "metrics": {
      "bad_review_rate": 0.18,
      "bad_review_distribution": {
        "物流": 35,
        "质量": 27,
        "售后": 16
      }
    },
    "description": "该商品差评率约为18%，差评主要集中在物流和质量维度。"
  }
}
```

若大模型规划或总结失败，当前实现会直接返回：

```json
{
  "sql_result": {
    "tool_calls": [],
    "metrics": {},
    "description": ""
  }
}
```

---

### 3.5 `visual_agent`

该 Agent 必须接入大模型，负责基于问题和统计结果生成可视化方案。

职责：
- 根据用户问题判断是否适合可视化表达。
- 根据统计结果自主决定哪些内容适合图表化。
- 根据统计结果选择合适图表类型。
- 输出结构化图表模板。

建议：
- 不直接让模型输出过于复杂的原生 ECharts 全量配置。
- 优先输出统一图表 DSL，再由后端模板层转换为 ECharts 配置。
- `router_agent` 只决定是否需要启用 `visual_agent`，不负责指定具体图表目标；具体图表决策由 `visual_agent` 自主完成。
- 若大模型不可用或图表结果无法通过落地校验，直接返回空图表，不再使用模板兜底。

建议输出：

```json
{
  "visual_result": {
    "charts": [
      {
        "chart_id": "chart_bad_review_distribution",
        "chart_type": "bar",
        "title": "差评维度分布",
        "description": "展示差评在各维度的数量分布",
        "x_axis": ["物流", "质量", "售后"],
        "series": [
          {
            "name": "差评数量",
            "data": [35, 27, 16]
          }
        ]
      }
    ]
  }
}
```

---

### 3.6 `rag_agent`

该 Agent 必须接入大模型，角色定位为电商评论分析专家。

职责：
- 根据用户问题和商品评论向量进行语义检索。
- 若当前请求没有商品上下文，则不执行商品级 RAG。
- 结合评论证据输出语义层面的原因归纳与结论支撑。

建议注意：
- `rag_agent` 负责证据分析，不直接承担最终输出责任。
- 它的主要产物应是检索证据与评论洞察，而不是最终回答 JSON。

建议输出：

```json
{
  "rag_result": {
    "queries": [
      "商品差评主要集中在哪些方面",
      "物流相关差评",
      "质量相关差评"
    ],
    "evidence": [
      {
        "content": "物流太慢了，等了一个星期才到。",
        "dimension": "物流",
        "score": 1,
        "similarity": 0.89
      },
      {
        "content": "做工一般，边角有瑕疵。",
        "dimension": "质量",
        "score": 2,
        "similarity": 0.84
      }
    ],
    "insight": "从评论语义看，差评原因主要集中在物流时效和产品做工问题。"
  }
}
```

---

### 3.7 `answer_agent`

建议新增该 Agent，用于统一整合各分析模块结果。

职责：
- 综合 `sql_result`、`rag_result`、`visual_result`。
- 生成候选回答草稿。
- 确保回答能够直接回应用户问题。

建议输出：

```json
{
  "answer_draft": {
    "answer": "该商品差评率约为18%，主要集中在物流和质量维度。从评论内容看，用户主要抱怨发货慢、到货延迟以及做工细节问题。",
    "answer_points": [
      "差评率约18%",
      "差评集中在物流和质量",
      "评论证据显示主要问题是时效和做工"
    ]
  }
}
```

---

### 3.8 `master_agent`

该 Agent 必须接入大模型，负责最终审查。

职责：
- 判断候选回答是否准确回应用户问题。
- 判断图表输出是否符合用户问题需求。
- 若结果满足要求，则允许返回前端。
- 若结果不满足要求，则指出缺失项并要求局部重跑。

建议系统提示词核心要求：
- 你是最终质量审查专家。
- 你需要审查回答和图表是否覆盖用户问题。
- 如不通过，需要明确指出缺失项以及建议从哪个 Agent 重跑。

建议输出：

```json
{
  "master_decision": {
    "decision": "pass",
    "reason": "回答覆盖了差评率、差评维度和评论原因，且提供了差评分布图。",
    "missing_items": []
  }
}
```

或：

```json
{
  "master_decision": {
    "decision": "retry",
    "reason": "用户明确要求可视化，但当前没有图表输出。",
    "missing_items": ["visual_result"],
    "retry_from": "visual_agent"
  }
}
```

## 4. 推荐的状态结构（LangGraph State）

建议新增统一的多 Agent 工作流状态对象，至少包含以下字段：

```python
class MultiAgentAnalysisState(TypedDict, total=False):
    user_id: int
    conversation_id: int
    user_message: str

    retry_count: int
    max_retry: int

    product_context: dict
    data_context: dict

    route_decision: dict

    sql_result: dict
    visual_result: dict
    rag_result: dict
    answer_draft: dict
    master_decision: dict

    final_response: dict
    error_message: str | None
```

说明：
- `retry_count` 用于记录当前已重试次数。
- `max_retry` 用于限制最大重试次数，建议初版设置为 1 或 2。
- 所有 Agent 共享同一状态对象，避免链路间参数拼装混乱。

## 5. 条件分支与重试规则

### 5.1 条件分支

建议工作流具备以下条件判断：

1. 若 `product_context.has_product = false`：
   - 禁止商品级 SQL / RAG / 可视化。
   - 由路由阶段输出澄清或普通问答处理路径。

2. 若 `route_decision.need_sql = true`：
   - 执行 `sql_agent`。

3. 若 `route_decision.need_visual = true`：
   - 在 SQL 结果准备完成后执行 `visual_agent`。

4. 若 `route_decision.need_rag = true` 且存在商品上下文：
   - 执行 `rag_agent`。

5. 所有已启用的分析节点完成后：
   - 执行 `answer_agent` 与 `master_agent`。

### 5.2 重试规则

不建议无限重跑，必须限制重试次数。

建议规则：
- `max_retry = 1` 或 `2`。
- 若 `master_agent` 输出 `retry`：
  - 根据 `retry_from` 局部重跑，而不是整条链路全部重跑。
- 若重试后仍未通过：
  - 可输出 `fallback_pass` 或友好提示，避免死循环。

推荐局部重跑策略：
- `retry_from = visual_agent` → 重跑 `visual_agent -> answer_agent -> master_agent`
- `retry_from = rag_agent` → 重跑 `rag_agent -> answer_agent -> master_agent`
- `retry_from = sql_agent` → 重跑 `sql_agent -> visual_agent(if needed) -> rag_agent(if needed) -> answer_agent -> master_agent`

## 6. 最终返回给前端的统一结构

建议最终输出 JSON 固定为：

```json
{
  "answer": "该商品差评率约为18%，主要集中在物流和质量维度。从评论内容看，用户主要抱怨发货慢、到货延迟以及做工细节问题。",
  "charts": [
    {
      "chart_id": "chart_bad_review_distribution",
      "chart_type": "bar",
      "title": "差评维度分布",
      "description": "展示差评在各维度的数量分布",
      "x_axis": ["物流", "质量", "售后"],
      "series": [
        {
          "name": "差评数量",
          "data": [35, 27, 16]
        }
      ]
    }
  ],
  "meta": {
    "product_id": 88,
    "used_agents": [
      "router_agent",
      "sql_agent",
      "visual_agent",
      "rag_agent",
      "answer_agent",
      "master_agent"
    ],
    "retry_count": 1
  }
}
```

说明：
- `answer` 为必填。
- `charts` 为可选，可为空数组。
- `meta` 用于调试、前端联调和后续排查。

## 7. 推荐的第一阶段落地顺序

为了降低一次性重构风险，建议按以下顺序推进。

### 第一步：协议先行
先补齐以下设计协议：
- 多 Agent 工作流节点定义
- 全局状态结构 `MultiAgentAnalysisState`
- 各 Agent 输出 JSON Schema
- 前端最终返回协议
- 局部重试规则

### 第二步：重构工作流编排
改造当前 `workflow.py`：
- 从固定串行流程升级为条件分支流程。
- 支持按 `route_decision` 动态调度不同 Agent。
- 支持 `master_agent` 驱动的局部重试。

### 第三步：优先替换 `router_agent`
先把当前规则版路由替换为“大模型 + 严格结构化输出”的版本。

### 第四步：封装 SQL 工具层
先固定统计工具函数边界，再让 `sql_agent` 调用这些工具。

### 第五步：新增 `visual_agent` 与 `answer_agent`
先打通统计结果到图表模板与回答整合这条链路。

### 第六步：增强 `rag_agent` 与 `master_agent`
最后再逐步加入更强的评论分析与局部重试逻辑。
