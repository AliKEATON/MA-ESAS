# 文档统一修订方案

## 核心功能
1. 普通对话与商品分析分为两条清晰链路，避免接口职责重复。
2. 商品链接解析后进入共享商品数据池，评论与向量数据按商品复用。
3. 分析任务异步执行，并向前端提供可持久化的进度查询能力。
4. 分析结果统一沉淀为文本总结、统计数据和图表配置。
5. 邮件推送作为扩展能力预留，不再和基础分析链路混写。

## 主要文件
- `docs/2.系统整体架构图.md` - 统一系统边界、模块职责和端到端流程
- `docs/4.数据库设计.md` - 统一主键/外部商品 ID、任务表和实体关系
- `docs/5.API接口定义.md` - 统一对话接口与分析接口的职责划分
- `backend/app/models/` - 后续数据库结构落地参考
- `backend/app/api/` - 后续接口落地参考
- `backend/app/schemas/` - 后续请求/响应结构落地参考

## 关键技术选型
- 前端基线：`frontend-streamlit/`（当前仓库实际实现）
- 后端：FastAPI + LangGraph + DrissionPage
- 存储：MySQL（持久化）、DuckDB（临时聚合分析）、ChromaDB（语义检索）

## 统一设计约束
- `products.id` 表示数据库内部主键。
- `products.external_product_id` 表示平台商品 ID，例如京东商品 ID。
- `products`、`comments`、ChromaDB 集合属于共享商品数据，不再直接挂 `user_id`。
- `conversations`、`messages`、`analysis_tasks`、`analysis_reports` 属于用户私有数据，通过 `user_id` 隔离。
- 商品分析只由分析接口显式触发，不再由“发送消息”接口隐式启动。
- 分析进度基于任务实体持久化，至少包含 `status`、`current_step`、`progress`、`error_message`。

## 修订顺序
1. 先重写系统整体架构图，统一前后端边界和分析链路。
2. 再重写数据库设计，补齐任务表并修正实体关系。
3. 最后重写 API 接口定义，确保请求参数和数据库字段一致。
